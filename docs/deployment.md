# Deployment Guide

SupportAI deploys as four independent pieces: **MongoDB Atlas** (database),
**Cloudinary** (file storage), **Render** (API + Redis + background workers),
and **Vercel** (frontend). This doc is the concrete, ordered path from zero to
a live instance.

## 1. MongoDB Atlas

1. Create a free account and a cluster (M10+ recommended once you have real
   traffic; Atlas Search/Vector Search is available on shared tiers too for
   development).
2. **Database Access** → add a user with a strong password (this becomes part
   of `MONGODB_URI`).
3. **Network Access** → add `0.0.0.0/0` to start (Render's IPs aren't static
   on the starter plan); tighten to Render's static outbound IPs (available
   on paid Render plans) once you have them.
4. Copy the connection string (`mongodb+srv://...`) — this is `MONGODB_URI`.
5. **Create the vector search index** (required for Phase 4's AI retrieval —
   nothing in application code can create this, it's a cluster-level index):
   Atlas UI → your cluster → **Search** tab → **Create Search Index** →
   **Atlas Vector Search** → JSON editor, on the `knowledgechunks` collection:

   ```json
   {
     "name": "knowledge_vector_index",
     "type": "vectorSearch",
     "fields": [
       { "type": "vector", "path": "embedding", "numDimensions": 768, "similarity": "cosine" },
       { "type": "filter", "path": "workspace" }
     ]
   }
   ```

   Use `numDimensions: 1536` instead if every workspace uses OpenAI embeddings
   (`text-embedding-3-small`) rather than Gemini's `text-embedding-004`. See
   `docs/database-design.md` for the full note on switching providers.

## 2. Cloudinary

1. Create a free account.
2. Dashboard → copy **Cloud name**, **API Key**, **API Secret** — these map
   directly to `CLOUDINARY_CLOUD_NAME` / `CLOUDINARY_API_KEY` /
   `CLOUDINARY_API_SECRET`. No bucket/folder setup needed; the app creates
   folders per workspace on upload.

## 3. Backend — Render

The repo root has a `render.yaml` Blueprint that provisions the API service
and a managed Redis instance together.

1. Render dashboard → **New** → **Blueprint** → connect this repo → Render
   reads `render.yaml` and proposes `supportai-api` (web service) +
   `supportai-redis`.
2. Before the first deploy, fill in the env vars marked `sync: false` in the
   blueprint (Render will prompt for these): `MONGODB_URI`, `WEB_APP_URL`
   (see step 4 below — a placeholder is fine for now), and whichever AI
   provider keys you're using (`GEMINI_API_KEY` at minimum, since it's the
   default provider for both chat and embeddings).
3. `JWT_ACCESS_SECRET`, `JWT_REFRESH_SECRET`, and `WIDGET_TOKEN_SECRET` are
   auto-generated by the blueprint (`generateValue: true`) — don't reuse
   these across environments.
4. Deploy. Render builds with `pnpm --filter @supportai/api build` and runs
   `node apps/api/dist/server.js`; `/health` is the configured health check
   path and reports real Mongo/Redis connectivity, not just process liveness.
5. Note the resulting service URL (`https://supportai-api.onrender.com` or
   similar) — this is what the frontend's `VITE_API_URL` points at.

If you'd rather not use the Blueprint, create the web service manually with
the same build/start commands and add a separate Redis instance (Render's
managed Redis, or an external one like Upstash) and wire `REDIS_URL` yourself.

## 4. Frontend — Vercel

1. Vercel dashboard → **New Project** → import this repo.
2. **Root Directory**: set to `apps/web` (monorepo — Vercel auto-detects Vite
   once the root is set correctly).
3. Environment variable: `VITE_API_URL` = `https://<your-render-service>.onrender.com/api/v1`.
4. Deploy. `apps/web/vercel.json` adds the SPA fallback rewrite so deep links
   (e.g. `/dashboard/inbox`) work on hard refresh instead of 404ing.

## 5. Close the loop

Frontend and backend now exist on unrelated domains
(`*.vercel.app` / `*.onrender.com`), which is exactly the cross-site setup
`common/auth/cookies.ts` is written for (`SameSite=None; Secure` in
production, no `Domain` attribute unless you set `COOKIE_DOMAIN`).

1. Copy the deployed Vercel URL.
2. Back in Render, update `WEB_APP_URL` to that exact URL (used for CORS and
   as the cookie's implicit origin) and redeploy the API service.
3. Visit the Vercel URL, register a workspace, and confirm login persists
   across a page reload (proves the refresh cookie round-trips correctly
   cross-site).

### Custom domain (optional)

If you put both apps under one domain (`app.example.com` for the frontend,
`api.example.com` for the backend), you can optionally set
`COOKIE_DOMAIN=.example.com` so the cookie is shared under the parent domain.
Not required — the default host-only + `SameSite=None` setup works without a
shared domain at all.

## 6. Post-deploy checklist

- [ ] Registered a workspace end-to-end and confirmed the AI widget panel
      (AI Settings → "Test your AI") gets a real streamed response
- [ ] Uploaded a knowledge base document and confirmed it reaches `ready`
      status (proves the BullMQ worker + Cloudinary + embeddings are wired)
- [ ] Confirmed the nightly analytics rollup is scheduled (`analytics.queue.ts`
      registers a repeatable BullMQ job on boot — check Render logs for
      "Connected to Redis" and no queue errors)
- [ ] Rotated any secrets that were generated with placeholder values during
      local testing
- [ ] Set Atlas backups/point-in-time recovery if this is real customer data
- [ ] Confirmed rate limits (`common/middleware/rate-limit.ts`) match your
      expected traffic — defaults are conservative for a fresh deployment
